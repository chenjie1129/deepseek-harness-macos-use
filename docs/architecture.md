# Agent Note: macOS GUI and browser use

Status: implemented

English | [中文](architecture.zh.md)

## Problem

The harness can edit files and run shell commands, but it has no explicit capability seam for applications that expose work only through a macOS GUI or a rendered browser page. Adding desktop control directly to one model-facing tool would mix operating-system execution, browser lifecycle, vision-provider configuration, loop policy, and result durability in one package.

## Decision

The implementation adds a four-package `macos-use` family. A dedicated GUI-model service sends screenshots to a configurable OpenAI-compatible vision endpoint, so GUI grounding does not require the driving model to accept image inputs. The endpoint, model, output cap, and credential reference are live visual plugin settings. P0 adds a semantic window-observation path alongside pixels: application and window discovery, exact-window capture, flattened Accessibility elements, and opaque element tokens that expire after a new snapshot or window-geometry change. The recommended deployment patch only mounts services; every adjustable agent setting remains on Plugin Configuration.

## Capability split

- `@deepseek-ai/dsh-macos-use` owns include-only foreground-window capture on a synthesized black main-display coordinate canvas, exact-window capture, application/window discovery, Accessibility state, target-guarded System Events actions, CoreGraphics pointer movement/dragging, and exact application launch through `ctx.subprocess`. Caller-supplied arbitrary AppleScript is always rejected.
- `@deepseek-ai/dsh-browser-use` owns one lazily launched Playwright Chromium process with a separate context, page, cookies, and observation state for each Harness Agent, plus an authenticated loopback proxy that validates, resolves, and IP-pins every outbound connection. It exposes selector, text, keyboard, coordinate, drag, and screenshot operations; a live browser-policy change retires every context and the proxy before the next action.
- `@deepseek-ai/dsh-gui-model` owns one independent screenshot-to-action request and validates the returned action union.
- `@deepseek-ai/dsh-tool-macos-use` owns the model-facing primitive schemas plus bounded desktop and browser action loops.

## Security and durability

macOS Accessibility and Screen Recording permissions remain host-controlled. Browser network and macOS application access are default-deny. Exact read and control grants, global application-deny rules, browser domain grants, and private-network access are all configured visually. A control grant must also have an equal or broader read grant so a native mutation cannot succeed and then be reported as failed merely because post-action evidence was unreadable. Deny rules override grants. The display-coordinate path never creates a full-display raster: it captures only the exact authorized foreground window and places it on a synthesized black canvas; excluded, unreadable, off-display, spanning, partially outside, or changing targets fail closed. An exact-window request for excluded content also fails closed. Caller-supplied arbitrary AppleScript remains unavailable. One-shot confirmation before every direct or model-selected GUI mutation is default-on. An operator should disable it only when an equivalent trusted safety or approval boundary exists; heuristic confirmation for destructive drags, keys, and task intent remains active when configured, but is not a semantic-effect guarantee.

Desktop screen, window, and Accessibility observations issue owner-bound, one-shot tokens. The service reserves a token before any asynchronous recheck and validates process, bundle, window identity, bounds, display geometry, mutation epoch, and—in the semantic path—element identity immediately before dispatch. Every native mutation shares one service-wide queue from revalidation through dispatch; dispatch advances the epoch and revokes all other pending desktop observations. Browser screenshot observations are owner/page/URL/expiry bound and carry a viewport digest that must match a fresh capture immediately before coordinate or keyboard dispatch. Navigation, redirects, subresources, and WebSockets are forced through an authenticated loopback proxy that revalidates the hostname, performs one DNS lookup for the outbound connection, rejects the full answer set if any address is non-public unless private access is enabled, and pins the socket to a numeric address while preserving Host and TLS SNI. Chromium DNS fallback, implicit loopback bypass, QUIC, workers, WebRTC, and WebTransport are disabled. This is defense in depth, not an operating-system network sandbox. A single-task lock, task deadline, command deadline, owner-scoped model abort, and global visual emergency stop bound autonomous control; this package family does not create a persistent operating-system permission grant.

The action loop is stop-on-uncertainty: malformed, oversized, unsupported, stale, or unverifiable actions do not fall through to a best guess. Model-declared `done` is necessary but not sufficient for success. The Host captures a fresh, atomic completion snapshot from the selected browser or macOS target and verifies the requested postcondition against that snapshot before setting `completed: true`.

Screenshot bytes are stored through `ctx.attachments`, while the driving model receives text references because its primary adapter rejects image tool-result content. GUI-model requests and intermediate decisions remain outside the driving Session log. A default-on presentation setting retains each available step screenshot as bounded, authorized UI-only result content. It covers completed tasks and plugin-catchable stopped/error results; a hard caller cancellation can preserve only short-lived best-effort progress because no tool result is produced. User-facing progress and durable task history replace the payload of `type` actions with a character-count placeholder; this does not redact text visible in screenshot pixels. The final task result retains the completion state, summary, redacted action/outcome list, verification status, and final screenshot reference. Stored copies are normalized to the active attachment limits without changing the original grounding pixels or action coordinates.

The tool package has Host and Client faces. The Host mounts its progress bridge through the Typert service lifecycle, binds live snapshots to the trusted Agent plus tool-call identity, and projects retained step images into `tool/result.data.meta.content`. The Session Controller authorizes those references and Session export includes their objects. The Client validates that metadata, loads images through the Session attachment route, and renders the task card through the keyed `tool.call.toolview` slot. The task output schema accepts the attachment service's optional `originalDimensions` metadata when normalization downscales a capture.

## Alternatives considered

- **Shell-only control.** Shell commands cannot reliably observe or operate applications whose meaningful state exists only in a rendered interface.
- **One monolithic plugin.** A single package would couple browser, desktop, provider, settings, tool schema, and loop changes, preventing independent replacement and focused tests.
- **Driving-model vision.** Requiring the main agent model to consume screenshots would make desktop capability depend on that model's modality support and would put large image results into ordinary conversation history.

## Verification

The plugin Vitest gate passes 330 tests across 22 files, and the Host and Client TypeScript projects plus the full integrated Harness build pass on the proven Harness `0.1.2-alpha.1` base. The suites cover target-guarded native-script construction, macOS service behavior, observation ownership/concurrency/staleness, Retina geometry, include-only foreground capture, task coordination and abort, GUI response parsing and bounded requests, browser isolation/network proxy/policy/actions, policy confirmations, atomic postcondition verification, typed-text output redaction, output-schema validation, visual settings-card registration, progress lifecycle, authorized attachment loading, and bounded task-loop execution. Separately, the prompt evaluator passes 19 tests across 8 files and a deterministic prompt-to-browser smoke against an independent HTTP oracle.

Release evidence records logic, type, build, package, compatibility, deterministic prompt, live provider, and rendered-UI gates separately. The rendered-UI gate bundles the actual `SettingsCards` and `GuiTaskView` components and verifies default-on, on-with-one-image, off-with-zero-images, clean console/request state, and no horizontal overflow. A deterministic fixture does not claim live third-party provider compatibility, and the current evidence does not claim an unlocked native-macOS application capture/action E2E or exact `0.1.2-alpha.5` compile/build/boot compatibility.

## Consequences

Products can compose desktop execution, browser execution, GUI grounding, and model-facing tools independently while keeping the driving model text-only. Every adjustable P0 agent option is presented visually in the GUI Model or GUI Agent card on the Plugin Configuration page. The recommended [`macos-use.cordis.patch.yml`](../integration/macos-use.cordis.patch.yml) therefore contains four service mounts and zero adjustable keys. The separation adds explicit installation requirements: Playwright Chromium must be present and the host must have operating-system permissions. Intermediate GUI steps are observable in live progress and the final result, optionally with their screenshots, but are not independently durable Session events.
